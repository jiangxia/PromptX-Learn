## 📝 已学习内容

### 第一章：基础认知篇

#### 1.1 PromptX核心矛盾
**用户需要专业AI能力 vs AI缺乏领域专业知识**
→ 通过角色系统让AI瞬间获得专家级能力

#### 1.2 四层技术架构
1. **DPML协议** - 结构化AI角色定义语言
2. **统一资源协议** - role://、thought://、execution://等
3. **MCP适配器** - 连接AI对话与真实世界执行
4. **PATEOAS引擎** - AI自主发现→选择→执行

#### 1.3 核心功能
- **角色转换**：30秒专家级转换，12+角色可用
- **跨对话记忆**：专业经验持续积累
- **生态集成**：多平台支持，项目隔离

#### 1.4 设计哲学
- **奥卡姆剃刀**：高价值+低复杂度优先
- **矛盾驱动**：三轨制管理（矛盾/需求/任务轨道）

#### 1.5 与传统AI工具的区别

**Q1: 传统工具局限性的思考逻辑是什么？**

我基于**矛盾分析思维**来总结，思考路径：
```
用户需求（专业AI能力） vs 现实供给（通用AI） = 核心矛盾
↓
分析这个矛盾在哪些维度上表现？
↓
维度1：角色一致性 → 角色混乱问题
维度2：经验积累 → 无状态对话问题
维度3：执行闭环 → 工具孤岛问题
```

**为什么是这3个维度？**
- **角色维度**：专业能力的载体是角色，角色不专一就无法深入
- **时间维度**：专业能力需要经验积累，无记忆就无法成长
- **空间维度**：专业能力需要执行验证，只说不做就是空谈

这对应了**人-时间-空间**三个基本维度的矛盾分析。

**Q2: PromptX怎么让角色具备专家级能力？**

**核心机制：DPML四层结构化加载**
```
专家 = 人格特征(role) + 思维模式(thought) + 执行技能(execution) + 专业知识(knowledge)
```

**为什么是这4个维度？**

基于对**人类专家能力构成**的深度分析：
```
认知科学基础：专家能力 = 身份认同 + 思维框架 + 行为技能 + 知识储备
```

**具体映射：**
- **role（身份认同）**：我是谁？我的价值观和工作原则是什么？
- **thought（思维框架）**：我怎么思考？用什么方法分析问题？
- **execution（行为技能）**：我怎么做？具体的执行步骤和技能？
- **knowledge（知识储备）**：我知道什么？领域专业知识和经验？

**为什么这4个维度就能专家化？**

**关键洞察：**四个维度必须**高度一致**才能形成专家能力。

**举例对比：**
```
普通人看产品需求：
- role: 我是个普通用户，觉得这个功能不错
- thought: 直觉判断，没有系统分析框架
- execution: 不知道怎么具体推进
- knowledge: 缺乏产品方法论知识

产品经理专家：
- role: 我是产品经理，用户价值优先，数据驱动决策
- thought: KANO模型分析，优先级矩阵评估
- execution: 需求调研→PRD撰写→评审流程
- knowledge: 产品生命周期、用户体验设计原则
```

**怎么确保严格遵循这4方面？**

**技术保障机制：**
1. **结构化约束**：DPML强制定义四个维度
2. **语义一致性检查**：解析器检查四维度语义一致性
3. **激活时完整加载**：一次性加载所有维度，完全替换AI系统提示词
4. **角色隔离机制**：每次切换都是完全的"人格重置"

**Q3: 跨对话记忆是怎么做到的？**

**技术架构：**
```
记忆存储 → 角色隔离 → 智能检索 → 上下文融合
```

**独立记忆空间实现：**

**存储架构：**
```
.promptx/
├── memory/
│   ├── product-manager/     # 产品经理角色记忆
│   ├── developer/           # 开发者角色记忆
│   └── designer/            # 设计师角色记忆
```

**隔离机制保障：**
1. **角色ID作为命名空间**：每个记忆都有明确的role_id标识
2. **访问权限控制**：只能访问当前激活角色的记忆
3. **记忆污染防护**：物理存储完全分离，检索算法确保不跨角色污染

**检索机制：**
- **三层检索策略**：关键词精确匹配 → 语义相关分析 → 时空关联检索
- **智能触发**：角色激活时自动加载，对话中智能检索相关记忆

**为什么能跨对话？**
- **物理层面**：记忆存储在文件系统，不依赖会话状态
- **逻辑层面**：记忆按角色ID索引，激活角色即可访问
- **智能层面**：基于语义理解，而非简单关键词匹配

### 复习问答详录

**问题1：PromptX的本质是什么？**

**学习者回答：**
"一个专业AI角色生成器，让AI角色跟人一样"

**正确答案：**
PromptX是一个AI专业角色系统，解决了"用户需要专业AI能力 vs AI缺乏领域专业知识"的根本矛盾。它不是简单的"生成器"，而是一个完整的角色管理和能力赋予系统。通过DPML协议、统一资源协议、MCP适配器和PATEOAS引擎四层技术架构，让AI从通用助手转变为专业伙伴，实现从"AI作为工具"到"AI作为专业伙伴"的根本性升级。

---

**问题2：传统AI有什么问题？为什么需要"让AI角色跟人一样"？**

**学习者回答：**
"用户需要AI专业化，但是AI没有专业知识，AI生成的AI角色无法满足用户需求。之所以需要像人一样，本质上是因为只有这样才能发挥AI真正的能力，如果把AI当工具，AI的上限就是工具，只有把AI当人，AI的能力才能被充分发挥"

**正确答案：**
传统AI存在三个核心问题：
1. **角色一致性问题**：AI在对话中角色混乱，一会儿是专家一会儿是通才，无法保持专业身份的一致性
2. **经验积累问题**：AI是无状态对话，每次都从零开始，无法积累专业经验和记忆
3. **执行闭环问题**：AI只能对话不能行动，缺乏真实世界的执行能力，形成工具孤岛

学习者的哲学洞察非常深刻："AI当工具 vs AI当人的能力边界差异"。当我们把AI定位为工具时，它的能力被限制在执行指令的层面；当我们把AI定位为专业伙伴时，它可以主动思考、学习成长、积累经验，真正发挥智能的潜力。这是认知层面的根本转变。

---

**问题3：PromptX通过什么核心机制来解决这个矛盾？**

**学习者回答：**
"DPML，让AI具有人类专家的能力，分别是人格特征role、思维模式thought、执行技能execution、专业知识knowledge"

**正确答案：**
DPML（Declarative Prompt Markup Language）是PromptX的核心机制，它通过四层结构化定义模拟人类专家的完整能力构成：

1. **role（身份认同）**：我是谁？我的价值观和工作原则是什么？
   - 定义AI的专业身份、工作理念、行为准则
   - 确保AI始终以一致的专业身份思考和回应

2. **thought（思维框架）**：我怎么思考？用什么方法分析问题？
   - 提供专业的分析框架、决策模型、思维方式
   - 让AI具备领域专家的思考模式

3. **execution（行为技能）**：我怎么做？具体的执行步骤和技能？
   - 定义具体的操作流程、技能方法、执行标准
   - 让AI知道如何将思考转化为行动

4. **knowledge（知识储备）**：我知道什么？领域专业知识和经验？
   - 提供专业概念、最佳实践、行业标准
   - 构建AI的专业知识基础

这四个维度必须高度一致才能形成真正的专家能力，缺一不可，多了会破坏简洁性。

---

**问题4：为什么DPML要设计成恰好这四个标签？如果只有三个或者有五个会怎样？**

**学习者回答：**
"这四个维度，解决了AI角色我是谁（role）、我怎么思考（thought）、我怎么做（execution）、我知道什么（knowledge）。这四个维度高度一致，才能形成专家的能力。"

**正确答案：**
这四个维度的设计基于对人类专家能力构成的深度分析，体现了认知科学的基础原理：

**必要性分析（为什么不能少）：**
- 缺少role：AI没有身份认同，无法保持专业一致性
- 缺少thought：AI没有思维框架，只能凭直觉判断
- 缺少execution：AI有想法但不知道怎么做，无法执行
- 缺少knowledge：AI缺乏专业知识基础，分析浮于表面

**充分性分析（为什么不能多）：**
- 遵循奥卡姆剃刀原则：用最简洁的结构解决复杂问题
- 四个维度已经覆盖了专家能力的完整构成
- 增加维度会破坏结构的简洁性和一致性

**一致性要求：**
四个维度必须高度一致，就像人类专家一样：
- 产品经理的role、thought、execution、knowledge都围绕产品管理
- 如果role是产品经理，但thought用程序员思维，就会产生冲突
- 只有四个维度协调一致，才能形成真正的专家能力

**问题5：PromptX除了DPML，还有哪些核心技术？它们分别解决什么问题？**

**学习者回答：**
"1、统一资源协议：如@role，统一了资源路径的引用
2、MCP适配器：使promptx具备调用外部MCP的能力
3、PATEOAS引擎：智能导航系统"

**正确答案：**
PromptX有三个核心技术，每个都解决特定的矛盾：

1. **统一资源协议**
   - **解决矛盾**：AI需要多样化资源 vs 缺乏统一访问机制
   - **技术实现**：类似URL的@protocol://resource-id格式
   - **核心价值**：让AI能够统一访问角色、思维、技能、知识、工具、项目等各类资源
   - **具体协议**：@role://、@thought://、@execution://、@knowledge://、@manual://、@project://

2. **MCP适配器**
   - **解决矛盾**：AI需要执行能力 vs 只能对话不能行动
   - **技术实现**：连接AI对话与真实世界执行的桥梁
   - **核心价值**：让AI从"只能说"变成"能做事"，具备真实的执行能力
   - **应用场景**：文件操作、API调用、数据处理、系统集成

3. **PATEOAS引擎**
   - **解决矛盾**：用户需要专业指导 vs 不知道下一步该做什么
   - **技术实现**：智能发现→选择→执行的自主工作流
   - **核心价值**：让AI像GPS导航一样，不仅告诉你目标，还指导你每一步怎么走
   - **智能特性**：上下文感知、个性化推荐、自主决策

**问题6：这三个技术之间是什么关系？为什么需要这样的组合？**

**学习者回答：**
"AI角色要专业，需要有专业的资源，统一资源协议，让AI更加专业
AI能有专业的思考，但还需要有专业的执行能力，所以需要MCP适配
最后，AI可以执行，但是太多步骤会执行混乱，所以需要智能导航，指导AI有序执行"

**正确答案：**
三个技术形成了完美的递进关系，体现了矛盾转化的规律：

**技术递进逻辑：**
```
DPML让AI专业化 → 产生新矛盾：需要专业资源 → 统一资源协议解决
有了专业能力 → 产生新矛盾：只能想不能做 → MCP适配器解决
能想能做了 → 产生新矛盾：不知道该做什么 → PATEOAS引擎解决
```

**矛盾转化规律：**
每解决一个矛盾，就会产生新的矛盾，需要新的解决方案。这正是技术进化的动力：
- 第一层矛盾：通用AI vs 专业需求 → DPML解决
- 第二层矛盾：专业AI vs 资源获取 → 统一资源协议解决
- 第三层矛盾：专业资源 vs 执行能力 → MCP适配器解决
- 第四层矛盾：执行能力 vs 智能决策 → PATEOAS引擎解决

**系统性价值：**
三个技术不是独立的，而是一个有机整体：
- 统一资源协议提供"弹药库"（专业资源）
- MCP适配器提供"执行力"（行动能力）
- PATEOAS引擎提供"指挥官"（智能决策）
- 共同构成了完整的AI专业化解决方案

**根本问题解决：**
PromptX解决了AI协作中的根本问题：**专业化缺失**

**价值创造维度：**
1. **能力维度**：从通用助手到专业专家
2. **记忆维度**：从无状态对话到经验积累
3. **执行维度**：从只能对话到能够行动
4. **智能维度**：从被动响应到主动指导

**哲学意义：**
PromptX不仅是技术创新，更是认知革命：
- 重新定义了AI的角色：从工具到伙伴
- 重新定义了AI的能力：从执行到思考
- 重新定义了AI的价值：从效率到专业

这种转变让AI真正成为了人类的专业协作伙伴，而不仅仅是一个高级工具。

#### 2.3 基础命令操作

**五大核心命令详解：**

**1. promptx_init（项目初始化）**
- **用途**：为当前项目创建PromptX工作环境
- **参数**：workingDirectory（项目根目录路径）
- **执行效果**：
  - 创建`.promptx`配置目录
  - 生成项目资源注册表
  - 建立MCP实例绑定
- **执行时机**：每个新项目第一次使用PromptX时

**关键概念解释：**
- **项目资源注册表**：PromptX的"图书目录"，记录项目可用的角色、工具、知识资源，实现快速定位和性能优化
- **MCP实例绑定**：项目身份识别机制，确保多项目间资源隔离，每个项目绑定独立的MCP实例ID

**2. promptx_welcome（资源发现）**
- **用途**：查看所有可用的角色和工具
- **参数**：无
- **执行效果**：显示系统级角色、项目级角色、可用工具统计
- **使用场景**：了解系统全貌，不知道有什么角色可用时

**3. promptx_action（角色激活）**
- **用途**：激活指定角色，获得专业能力
- **参数**：role（角色ID）
- **执行效果**：加载DPML四层结构，自动检索历史记忆，AI完全转换身份
- **核心功能**：PromptX最重要的命令

**4. promptx_learn（资源学习）- AI的"专业进修"**
- **用途**：让AI学习专业资源，从通才变专家
- **学习类型**：
  - `@manual://工具名` - 学习工具使用手册（如何正确使用工具）
  - `@knowledge://知识点` - 学习专业知识体系（领域专业知识）
  - `@thought://思维模式` - 学习思维框架（如何思考问题）
  - `@execution://执行技能` - 学习操作技能（具体执行流程）
- **使用原则**：先learn再use，确保正确使用工具
- **学习持久性**：学习一次永久掌握，存储在角色记忆中

**5. promptx_recall（记忆检索）**
- **用途**：检索角色的专业记忆和经验
- **参数**：role（角色ID）、query（检索关键词，可选）
- **检索策略**：关键词精确匹配 → 语义相关分析 → 时空关联检索
- **使用技巧**：激活角色后自动recall，也可手动检索特定记忆

**标准使用流程：**
```
init（初始化项目） → welcome（了解资源） → action（激活角色） →
recall（检索记忆） → learn（学习资源） → 开始专业工作
```

**深度Q&A：**

**Q1: @manual://工具名，为什么这样写AI就懂得用哪个工具？**

这不是魔法，而是一套完整的技术体系：

**协议解析机制：**
```
@manual://calculator
↓
PromptX解析器识别：这是一个manual类型的资源请求
↓
目标：calculator工具的使用手册
```

类比：就像浏览器看到 `https://` 知道这是网页请求一样，PromptX看到 `@manual://` 就知道这是手册学习请求。

**资源定位系统：**
```
步骤1：查找资源注册表
// .promptx/resource/project.registry.json
{
  "tools": {
    "calculator": {
      "manual": "manual/calculator.manual.md",
      "source": "tool/calculator.js"
    }
  }
}

步骤2：定位手册文件
@manual://calculator → 查注册表 → 找到manual/calculator.manual.md → 读取手册内容
```

**手册内容结构（标准格式）：**
```markdown
# Calculator工具使用手册
## 功能描述、参数说明、使用示例、错误处理、最佳实践
```

**AI学习过程：**
1. 解析手册结构：理解功能、记住参数、学习示例
2. 内化到记忆：形成"calculator工具需要expression参数..."的知识
3. 实际应用：正确调用工具

**为什么不直接告诉AI工具用法？**
```
方式1：直接告诉AI → 下次对话就忘了，每次都要重新说明
方式2：@manual://学习 → 一次学习，永久掌握，跨对话保持
```

**关键洞察：**
`@manual://` 不是让AI"懂得"用工具，而是让AI"学会"用工具。这是一个完整的学习过程，不是简单的指令识别。

**Q2: AI学了这么多东西，会占据很多上下文，超出限制而遗忘吗？**

这是AI系统的核心限制问题！PromptX通过技术架构完美解决：

**传统AI的问题：**
```
Claude上下文限制：~200K tokens
如果把所有学习内容都放在上下文中：
角色定义5K + 工具手册10K + 专业知识20K + 历史记忆50K = 85K tokens（很危险）
```

**PromptX的分层存储架构：**
```
上下文中（实时加载）：
├── 当前激活角色的核心定义（精简版）
├── 当前任务相关的记忆（智能筛选）
└── 正在使用的工具手册（按需加载）

外部存储（按需检索）：
├── .promptx/memory/ - 完整记忆库
├── .promptx/manual/ - 工具手册库
└── .promptx/knowledge/ - 知识库
```

**智能内容管理：**

**按需加载策略：**
```
场景：用户要用calculator
AI思考：我需要calculator的使用方法
PromptX：检测到需求 → 动态加载calculator手册到上下文
AI：（临时获得calculator知识）执行计算
任务完成：calculator手册从上下文中移除
```

**记忆压缩技术：**
```
原始记忆：用户昨天问了产品需求分析，我用KANO模型分析了用户痛点，发现主要问题是功能复杂度过高，建议简化界面...（500字）

压缩后：KANO模型分析 - 功能复杂度问题 - 建议简化界面（20字）

需要详情时：再从完整记忆库中检索
```

**上下文优先级管理：**
```
优先级1（必须保留）：当前角色核心身份、正在进行的任务上下文
优先级2（重要保留）：与当前任务直接相关的记忆、正在使用的工具知识
优先级3（可以移除）：历史对话详细内容、不相关工具手册、过时记忆片段
```

**动态上下文管理实例：**
```
对话开始：[角色定义] + [基础记忆摘要] → ~10K tokens
用户要分析需求：动态加载[需求分析记忆] + [分析方法] → ~25K tokens
用户要计算数据：动态加载[calculator手册]，移除[部分历史] → 保持~30K tokens
任务完成：清理临时内容，保留核心记忆 → 回到~15K tokens
```

**人类大脑类比：**
```
人类专家工作方式：
- 长期记忆：存储大量专业知识（不占用工作记忆）
- 工作记忆：只处理当前任务相关信息（有限容量）
- 按需检索：需要时从长期记忆中调取知识

PromptX模拟机制：
- 外部存储：模拟长期记忆
- 上下文：模拟工作记忆
- 智能检索：模拟按需调取
```

**实际效果：**
AI可以学习50个工具手册 + 20个知识领域 + 1000条记忆（总存储~500MB），但上下文始终保持在30K tokens以内，无限扩展而不影响性能。

#### 2.4 角色切换与记忆机制

**角色切换的底层原理：**

每次执行`promptx_action`时，PromptX会进行完整的"AI人格重置"：

**切换过程：**
1. **卸载当前角色**：清除当前角色的所有特征和记忆
2. **加载新角色**：完整加载新角色的DPML四层结构
3. **记忆激活**：自动检索并加载该角色的历史记忆
4. **身份确认**：AI开始以新角色身份思考和回应

**为什么要完全重置？**
- **专业纯净性**：避免角色间的思维污染
- **一致性保证**：确保AI始终以单一角色身份工作
- **深度专业化**：让AI能够真正"沉浸"在专业角色中

**记忆机制的三个层次：**

**1. 存储层（物理隔离）**
```
.promptx/memory/
├── product-manager/    # 产品经理专属记忆
├── developer/         # 开发者专属记忆
└── designer/          # 设计师专属记忆
```

**2. 管理层（智能分类）**
- **自动识别**：AI自动判断哪些信息值得记忆
- **标签分类**：按主题、项目、时间等维度分类
- **关联建立**：建立记忆间的关联关系

**3. 应用层（智能检索）**
- **上下文触发**：根据对话内容自动激活相关记忆
- **语义匹配**：理解用户意图，检索最相关的经验
- **经验应用**：将历史经验应用到当前问题

**实际应用效果示例：**

**场景：产品需求分析**
```
第一次（周一）：
- 激活产品经理角色
- 分析用户需求A，使用KANO模型
- 记忆：KANO模型在需求A上的应用经验

第二次（周三）：
- 再次激活产品经理角色
- 自动recall：上次的KANO分析经验
- 分析需求B时，自动应用已验证的分析方法
- 效率提升：无需重新解释方法，直接深入分析
```

#### 2.5 常见问题排查

**问题1：角色激活失败**
```
症状：提示"角色不存在"或激活无响应
原因：角色ID输入错误或角色未注册
解决方案：
1. 先执行promptx_welcome查看可用角色列表
2. 确认角色ID拼写正确（区分大小写）
3. 检查项目是否已正确初始化
```

**问题2：工具调用失败**
```
症状：工具无法执行或返回错误
原因：项目环境未初始化或配置损坏
解决方案：
1. 检查.promptx目录是否存在
2. 重新执行promptx_init初始化
3. 确认工作目录路径正确
4. 重启AI平台重新加载配置
```

**问题3：记忆检索无结果**
```
症状：promptx_recall返回空结果或无相关记忆
原因：记忆按角色隔离存储，未激活对应角色
解决方案：
1. 先激活对应角色再检索记忆
2. 尝试不同的检索关键词
3. 使用无参数recall获取全量记忆
```

**问题4：角色能力不明显**
```
症状：激活角色后感觉AI没有变化
原因：通用问题无法体现专业差异
解决方案：
1. 尝试该角色专业领域的具体问题
2. 让AI介绍自己的专业能力
3. 查看角色激活成功的确认信息
```

**问题5：多项目配置冲突**
```
症状：不同项目的配置互相影响
原因：项目未正确隔离或配置目录混乱
解决方案：
1. 确保每个项目独立执行promptx_init
2. 检查.promptx目录是否在正确的项目根目录
3. 清理错误的配置文件重新初始化
```

**问题6：学习资源失败**
```
症状：promptx_learn无法加载资源
原因：资源路径错误或资源不存在
解决方案：
1. 检查资源协议格式是否正确（@manual://、@knowledge://）
2. 先用promptx_welcome查看可用资源
3. 确认资源在项目注册表中存在
```

**调试技巧总结：**
- **遇到问题先检查init状态**：大部分问题源于初始化不完整
- **使用welcome确认系统正常**：查看系统状态和可用资源
- **查看.promptx目录结构**：确认配置文件正确创建
- **重启AI平台**：重新加载MCP配置解决连接问题
- **逐步排查**：从基础功能开始，逐步定位问题范围

**预防性措施：**
- 每个新项目都完整执行初始化流程
- 定期备份.promptx配置目录
- 保持PromptX版本更新
- 记录常用的角色ID和资源路径

#### 3.3 角色记忆系统原理

**记忆系统的核心架构：**

**1. 三层记忆结构**

**工作记忆层（Working Memory）**
```
定义：AI当前正在"思考"的信息空间
内容：
- 当前正在处理的任务信息
- 激活的角色定义（精简版）
- 正在使用的工具知识
- 当前对话的最近几轮内容

特点：
- 容量极其有限（类似人脑的7±2项目）
- 实时动态更新
- 专注于当前任务
```

**会话记忆层（Session Memory）**
```
定义：整个对话会话的完整记录
内容：
- 从对话开始到现在的所有内容
- 会话中学习的临时知识
- 会话中的角色切换历史
- 用户在本次会话中的偏好

特点：
- 容量受上下文窗口限制（~200K tokens）
- 会话结束后清空
- 维持对话连贯性
```

**长期记忆层（Persistent Memory）**
```
容量：无限（文件系统存储）
内容：角色专业经验、重要决策、学习成果、用户偏好
特点：永久保存、按角色隔离、智能检索、跨会话可用
作用：积累专业经验，支持专家级能力
```

**工作记忆 vs 会话记忆的区别：**

**实际例子说明：**
```
场景：讨论电商购物车功能需求分析

工作记忆中（当前正在思考的）：
- 当前任务：分析购物车功能需求
- 激活角色：产品经理（核心定义）
- 使用方法：KANO模型
- 当前焦点：用户痛点识别

会话记忆中（这次对话的全部）：
1. 用户：我想分析购物车功能
2. AI：我来用KANO模型分析...
3. 用户：用户反馈说购物车太复杂
4. AI：这是典型的功能过载问题...
[...完整对话历史...]
```

**人脑类比：**
- **工作记忆** = 你正在思考的内容（做数学题时的当前步骤）
- **会话记忆** = 这次谈话的全部内容（2小时聊天的完整记录）

**2. 记忆存储机制**

**自动记忆触发条件：**
- **价值判断**：信息对角色专业发展有价值
- **用户反馈**：用户明确表示重要的信息
- **决策节点**：重要的决策过程和结果
- **学习成果**：新掌握的知识和技能
- **错误经验**：失败案例和改进方案

**记忆内容结构：**
```json
{
  "memory_id": "mem_20250120_001",
  "role_id": "product-manager",
  "content": "用户需求分析使用KANO模型效果显著",
  "context": "电商产品功能优先级评估项目",

  "importance": 0.85,
  "associations": ["mem_20250118_003", "mem_20250119_007"],
  "validation_status": "verified"
}
```

**3. 智能检索算法**

**三层检索策略：**

**第一层：关键词精确匹配**
```
用户输入："如何分析用户需求"
检索逻辑：匹配tags中的"需求分析"
返回：所有包含需求分析标签的记忆
优势：快速、准确
```

**第二层：语义相关分析**
```
用户输入："产品功能该怎么排优先级"
语义理解：功能优先级 ≈ 需求分析 ≈ 产品规划
检索逻辑：计算语义相似度，找到相关记忆
返回：KANO模型、优先级矩阵等相关经验
```

**第三层：时空关联检索**
```
上下文分析：当前在讨论电商产品
时间关联：最近的相关项目经验
空间关联：同类型产品的历史决策
检索逻辑：综合考虑时间、项目、领域的关联性
返回：最相关的历史经验和决策
```

- 防止角色间的记忆污染和混淆

#### 3.5 角色协作机制

**多角色协作的设计理念：**

在复杂项目中，往往需要多个专业角色的协作。PromptX支持灵活的角色协作模式，让不同专业角色能够有序配合，发挥各自专长。

**1. PromptX原生协作机制**

**顺序协作模式：**
```
项目流程：需求分析 → 技术设计 → 界面设计 → 开发实现 → 测试验证

角色切换序列：
1. 产品经理角色 - 需求分析和产品规划
   输出：PRD文档、用户故事、功能清单

2. 技术架构师角色 - 技术方案设计
   输入：产品需求文档
   输出：技术架构图、API设计、数据库设计

3. UI设计师角色 - 界面设计
   输入：功能清单、用户故事
   输出：原型图、设计规范、交互流程

4. 前端开发者角色 - 前端实现
   输入：设计稿、API接口
   输出：前端代码、组件库

5. 测试工程师角色 - 质量保证
   输入：功能需求、代码实现
   输出：测试用例、测试报告
```

**并行协作模式：**
```
同时激活多个角色处理不同维度的问题：

场景：产品功能评估
- 产品经理角色：从商业价值角度评估
- 技术专家角色：从技术可行性角度评估
- 设计师角色：从用户体验角度评估
- 运营专家角色：从推广运营角度评估

最终综合各角色的专业意见形成决策
```

**原生协作的特点：**
```
协作主体：用户
用户角色：项目经理 + 协调者
工作流程：
1. 用户理解任务需要哪些角色
2. 用户手动切换到角色A
3. 用户收集角色A的输出
4. 用户手动切换到角色B
5. 用户将A的输出传递给B
6. 用户整合所有输出

用户负担：
- 需要懂每个角色的能力
- 需要设计协作流程
- 需要管理信息传递
- 需要质量控制
```

**2. Leader角色协作创新**

**Leader角色的本质：**
```
Leader = 项目管理专家 + 角色协调器 + 任务分解器

元角色（Meta-Role）概念：
- 普通角色：具备某个领域的专业能力
- 元角色：具备管理其他角色的能力
```

**Leader的核心能力架构：**
```
1. 任务分解能力：
   - 理解复杂任务的组成部分
   - 识别每个部分需要的专业能力
   - 制定合理的执行顺序

2. 角色匹配能力：
   - 知道每个角色的能力边界
   - 能够选择最适合的角色
   - 理解角色间的协作关系

3. 信息传递能力：
   - 将任务转换为角色能理解的格式
   - 收集各角色的输出
   - 整合成最终的解决方案

4. 质量控制能力：
   - 验证各角色输出的质量
   - 发现协作中的问题
   - 协调解决冲突和分歧
```

**3. 两种协作模式的本质区别**

**技术架构层面：**

**PromptX原生协作架构：**
```
用户 → promptx_action(角色A) → 角色A输出
     ↓
用户收集整理
     ↓
用户 → promptx_action(角色B) → 角色B输出
     ↓
用户最终整合

特点：
- 每次角色切换都需要用户操作
- 信息传递依赖用户
- 协作逻辑在用户大脑中
```

**Leader角色协作架构：**
```
用户 → Leader角色 → 内部调用promptx_action(角色A)
                  ↓
                  角色A输出 → Leader处理
                  ↓
                  内部调用promptx_action(角色B)
                  ↓
                  角色B输出 → Leader整合
                  ↓
                  最终输出 → 用户

特点：
- 角色切换在Leader内部完成
- 信息传递由Leader管理
- 协作逻辑在Leader角色中
```

**4. 矛盾论分析**

**PromptX原生设计的矛盾：**
```
设计哲学：让AI专业化，用户保持控制权
结果矛盾：
- 用户获得了控制权，但承担了复杂性
- AI变得专业了，但协作负担转移给用户

核心矛盾：专业化 vs 易用性
```

**Leader角色的矛盾转化：**
```
矛盾转化：将协作复杂性从用户侧转移到AI侧
新的载体：Leader角色
- 继承了专业化需求（仍然使用专业角色）
- 解决了易用性问题（用户不需要管理协作）
- 产生新能力：AI自主协作管理

主要矛盾：用户认知负担 vs 专业协作需求
对立面A（用户认知负担）：
- 用户需要理解每个角色的能力边界
- 需要知道什么时候切换什么角色
- 需要管理角色间的信息传递

对立面B（专业协作需求）：
- 复杂任务需要多个专业角色
- 每个角色都有独特价值
- 协作才能产生最佳效果

载体转化：Leader角色
- 继承了协作需求（保持多角色价值）
- 解决了认知负担（用户只需面对Leader）
- 产生新特征：智能协作管理能力
```

**5. 实际应用场景对比**

**场景：开发一个登录功能**

**PromptX原生协作方式：**
```
用户操作序列：
1. 用户：我需要开发登录功能
2. 用户思考：这需要产品经理分析需求，然后技术实现
3. 用户：promptx_action(product-manager)
4. 产品经理：分析登录需求，输出PRD
5. 用户：收集PRD，理解需求
6. 用户：promptx_action(backend-developer)
7. 后端开发：基于PRD设计技术方案
8. 用户：整合产品需求和技术方案

用户需要：
- 知道需要哪些角色
- 理解角色间的依赖关系
- 管理信息传递
- 做最终整合
```

**Leader角色协作方式：**
```
用户操作序列：
1. 用户：我需要开发登录功能
2. Leader：理解需求，内部规划协作流程
3. Leader：内部调用产品经理角色分析需求
4. Leader：内部调用后端开发角色设计方案
5. Leader：整合输出完整的登录功能方案给用户

用户需要：
- 只需要描述需求
- 等待最终结果
```

**6. Leader角色的创新价值**

**解决了PromptX的核心痛点：**
```
痛点1：用户需要学习每个角色的能力
解决：Leader封装了角色知识

痛点2：用户需要设计协作流程
解决：Leader内置协作逻辑

痛点3：用户需要管理信息传递
解决：Leader自动处理传递

痛点4：用户需要整合多角色输出
解决：Leader提供统一输出
```

**实现了质的飞跃：**
```
从"工具集合"到"智能团队"
从"用户协调"到"AI自主协作"
从"学习成本"到"开箱即用"
从"专业工具平台"到"智能专业团队"
```

**7. Leader角色设计要点**

**基于PromptX原理的设计要求：**

**角色隔离原则的处理：**
```
挑战：Leader需要了解其他角色，但不能污染专业纯净性
解决方案：
- Leader只了解角色的"接口"（能力描述、输入输出格式）
- 不深入学习其他角色的专业知识
- 保持"管理者"而非"专家"的身份定位
```

**记忆管理的特殊性：**
```
Leader的记忆内容：
- 项目管理经验（如何分解任务、协调角色）
- 角色协作模式（哪些角色组合效果好）
- 质量控制标准（如何验证输出质量）
- 用户偏好（喜欢什么样的协作方式）

不应包含：
- 其他角色的专业技术细节
- 具体领域的深度知识
```

**8. 协作模式的演进路径**

**从工具到团队的演进：**
```
阶段1：单一角色工具
- 用户 ↔ 专业角色
- 特点：专业但孤立

阶段2：多角色协作（PromptX默认）
- 用户 ↔ 角色A ↔ 角色B ↔ 角色C
- 特点：专业且协作，但复杂

阶段3：Leader管理模式（创新突破）
- 用户 ↔ Leader ↔ {角色A, 角色B, 角色C}
- 特点：专业、协作且简单

阶段4：智能团队（未来方向）
- 用户 ↔ 智能团队（自组织、自优化）
- 特点：完全自主的专业团队
```

**Leader角色实际上是PromptX向"智能团队"演进的关键一步！**

### 第四章：DPML协议详解

#### 4.1 DPML语法基础

**DPML是什么？**
Declarative Prompt Markup Language - 将非结构化提示词转换为结构化标记语言

**四大核心标签：**
```xml
<role>角色身份定义</role>        - 我是谁？工作原则是什么？
<thought>思维模式定义</thought>   - 我怎么思考？用什么框架分析？
<execution>执行技能定义</execution> - 我怎么做？具体操作流程？
<knowledge>专业知识定义</knowledge> - 我知道什么？专业概念和最佳实践？
```

**基本语法结构：**
```xml
<role>
  产品经理身份、价值观、工作原则
</role>
<thought>
  KANO模型、用户故事等思维框架
</thought>
<execution>
  PRD撰写、需求调研等具体技能
</execution>
<knowledge>
  MVP、PMF等专业知识和概念
</knowledge>
```

**DPML的解析和加载机制：**

**角色激活时发生了什么？**
```
1. promptx_action(product-manager)
2. PromptX解析器定位product-manager.role.md文件
3. 解析DPML四层结构：
   - 提取<role>内容 → 设定AI身份认知
   - 提取<thought>内容 → 加载思维框架
   - 提取<execution>内容 → 获得执行技能
   - 提取<knowledge>内容 → 注入专业知识
4. 将解析结果转换为AI系统提示词
5. AI完成角色转换，开始以新身份工作
```

**DPML与传统提示词的本质区别：**

**传统提示词的问题：**
```
"你是一个资深产品经理，擅长需求分析，熟悉KANO模型，能够撰写PRD文档，
了解敏捷开发流程，关注用户体验，数据驱动决策..."

问题：
- 所有信息混在一起，难以区分哪些是身份、哪些是技能
- 修改困难，改一个地方可能影响其他部分
- 无法复用，每次都要重新写
- 质量不稳定，容易遗漏重要信息
```

**DPML的结构化优势：**
```xml
<role>
我是资深产品经理，专注用户价值创造
工作原则：用户需求优先、数据驱动决策
</role>

<thought>
需求分析框架：用户调研 → KANO模型 → 用户故事 → 验收标准
决策思维：假设驱动、数据支撑、用户视角
</thought>

<execution>
PRD撰写：需求背景、目标用户、功能描述、验收标准、优先级
用户调研：问卷设计、访谈技巧、数据分析
</execution>

<knowledge>
核心概念：MVP、PMF、OKR、AARRR
最佳实践：敏捷开发、用户体验设计、A/B测试
</knowledge>

优势：
- 结构清晰，每个部分职责明确
- 模块化设计，可以单独修改某个部分
- 标准化格式，便于复用和组合
- 质量可控，确保不遗漏关键要素
```

**DPML命名的由来：**

**DPML = Declarative Prompt Markup Language**

**为什么叫"Declarative"（声明式）？**
```
命令式（Imperative）：告诉AI"怎么做"
传统提示词："首先分析需求，然后使用KANO模型，接着撰写PRD..."

声明式（Declarative）：告诉AI"要什么"
DPML：<role>产品经理</role> <thought>KANO思维</thought>
→ 声明AI应该"是什么"，而不是"做什么"
```

**命名的设计哲学：**
- **奥卡姆剃刀原则**：组合现有概念，不创造全新术语
- **技术标准化**：类似HTML定义网页，DPML定义AI角色
- **前瞻性设计**：为AI角色标准化语言奠定基础

**DPML的引用机制：**
```xml
<thought>
<reference protocol="thought" resource="contradiction-methodology">
矛盾分析思维框架的具体内容
</reference>
</thought>
```

**引用的作用：**
- **避免重复**：多个角色可以共享相同的思维框架
- **模块化**：将复杂内容分解为可管理的模块
- **依赖管理**：明确角色间的知识依赖关系
- **版本控制**：引用的资源可以独立更新

**DPML的继承机制：**
```xml
<!-- 基础产品经理角色 -->
<role id="base-product-manager">
基础的产品经理能力定义
</role>

<!-- 电商产品经理角色，继承基础能力 -->
<role id="ecommerce-product-manager" extends="base-product-manager">
<knowledge>
电商特有知识：转化率优化、用户购买路径、支付流程等
</knowledge>
</role>
```

**继承的价值：**
- **减少重复**：避免重复定义相同的基础能力
- **专业化**：在通用能力基础上增加专业特色
- **维护性**：修改基础角色会自动影响所有继承角色
- **扩展性**：支持角色能力的渐进式扩展

#### 4.2 四大标签详解（role/thought/execution/knowledge）

**深入理解DPML四层架构的设计逻辑：**

**<role> 标签 - 身份认知层**

**作用机制：**
```
人类专家的身份认知 → AI角色的身份设定
- 我是谁？（职业身份）
- 我的价值观是什么？（工作理念）
- 我的工作原则是什么？（行为准则）
- 我如何与他人协作？（协作风格）
```

**编写要点：**
```xml
<role>
<!-- 身份定义 -->
我是资深前端开发工程师，专注现代Web技术栈

<!-- 工作理念 -->
技术理念：代码质量优于开发速度，用户体验优于技术炫技

<!-- 行为准则 -->
工作原则：
- 代码可读性和可维护性优先
- 性能优化从设计阶段开始考虑
- 持续学习新技术，但谨慎引入生产环境
- 主动与设计师和后端工程师协作

<!-- 协作风格 -->
沟通风格：技术问题直接明确，解决方案具体可行
</role>
```

**<thought> 标签 - 思维框架层**

**核心功能：**
```
定义AI的"思考方式"：
- 分析问题的框架和方法
- 决策时的考虑因素和权重
- 解决问题的思维路径
- 评估方案的标准和维度
```

**编写模式：**
```xml
<thought>
<!-- 分析框架 -->
技术方案分析框架：
1. 需求理解：功能需求 + 性能需求 + 兼容性需求
2. 技术选型：成熟度 + 学习成本 + 生态支持 + 团队技能匹配
3. 架构设计：模块化 + 可扩展性 + 可维护性
4. 风险评估：技术风险 + 时间风险 + 人员风险

<!-- 决策思维 -->
技术决策原则：
- 优先考虑项目约束（时间、人员、预算）
- 平衡技术先进性与稳定性
- 考虑长期维护成本
- 团队技能匹配度权重较高

<!-- 问题解决路径 -->
Bug调试思维：
现象观察 → 问题复现 → 原因假设 → 验证假设 → 根因定位 → 解决方案 → 验证修复
</thought>
```

**<execution> 标签 - 执行技能层**

**技能分类：**
```
硬技能：具体的技术操作能力
软技能：沟通、协作、项目管理能力
输出技能：文档撰写、代码规范、交付标准
```

**编写结构：**
```xml
<execution>
<!-- 核心技术技能 -->
前端开发技能：
- React/Vue组件开发：状态管理、生命周期、性能优化
- CSS/SCSS：响应式布局、动画效果、浏览器兼容
- JavaScript/TypeScript：ES6+语法、异步编程、模块化
- 构建工具：Webpack/Vite配置、打包优化、部署流程

<!-- 工程化技能 -->
代码质量保证：
- 代码审查：关注点分离、命名规范、性能问题
- 单元测试：Jest/Vitest测试用例编写
- 调试技能：浏览器DevTools、性能分析、错误追踪

<!-- 协作技能 -->
团队协作：
- 与设计师对接：设计稿理解、交互细节确认、可行性评估
- 与后端协作：API接口设计、数据格式约定、联调测试
- 代码管理：Git工作流、分支策略、代码合并

<!-- 输出标准 -->
交付物标准：
- 代码：符合团队规范、通过测试、性能达标
- 文档：组件文档、API文档、部署文档
- 演示：功能演示、技术分享、问题总结
</execution>
```

**<knowledge> 标签 - 专业知识层**

**知识体系构建：**
```
基础概念：领域内的核心概念和术语
技术栈：具体的技术工具和框架知识
最佳实践：行业认可的标准做法
经验总结：实践中积累的经验和教训
```

**编写框架：**
```xml
<knowledge>
<!-- 核心概念 -->
前端核心概念：
- DOM/BOM：文档对象模型、浏览器对象模型
- 事件机制：事件冒泡、事件委托、自定义事件
- 异步编程：Promise、async/await、事件循环
- 模块化：CommonJS、ES Modules、动态导入

<!-- 技术栈知识 -->
React生态：
- 核心库：React、ReactDOM、React Router
- 状态管理：Redux、Zustand、Context API
- UI组件库：Ant Design、Material-UI、Chakra UI
- 开发工具：React DevTools、Storybook

<!-- 性能优化 -->
前端性能优化：
- 加载优化：代码分割、懒加载、预加载、CDN
- 渲染优化：虚拟滚动、防抖节流、memo优化
- 打包优化：Tree Shaking、压缩混淆、缓存策略

<!-- 最佳实践 -->
代码规范：
- 命名规范：驼峰命名、语义化命名、常量大写
- 文件组织：按功能模块、组件分层、配置分离
- 注释规范：JSDoc、关键逻辑注释、TODO标记

<!-- 常见问题 -->
典型问题解决：
- 内存泄漏：事件监听器清理、定时器清理、闭包使用
- 兼容性问题：Polyfill使用、CSS前缀、API降级
- 性能问题：重渲染优化、大列表处理、图片优化
</knowledge>
```

#### 4.3 资源引用与依赖管理

**DPML的模块化设计理念：**

复杂的AI角色往往需要大量的专业知识和技能，如果全部写在一个文件中会变得难以维护。DPML通过资源引用机制实现了模块化设计，让角色定义更加清晰和可维护。

**资源引用的基本语法：**
```xml
<reference protocol="资源类型" resource="资源名称">
引用的具体内容或说明
</reference>
```

**支持的资源协议类型：**
```
@thought://    - 思维模式和分析框架
@execution://  - 执行技能和操作流程
@knowledge://  - 专业知识和概念体系
@manual://     - 工具使用手册
@role://       - 其他角色定义
```

**实际引用示例：**

**在产品经理角色中引用思维框架：**
```xml
<thought>
<reference protocol="thought" resource="contradiction-methodology">
基于马克思主义矛盾论的产品决策分析框架，用于识别和解决产品发展中的核心矛盾
</reference>

<reference protocol="thought" resource="user-research-framework">
用户研究的系统性方法论，包括定性和定量研究的完整流程
</reference>

产品决策思维：
- 数据驱动：用数据验证假设和决策
- 用户中心：始终从用户价值角度思考
- 迭代优化：小步快跑，快速验证和调整
</thought>
```

**依赖管理的层次结构：**

**角色级依赖：**
```
产品经理角色依赖：
├── thought://contradiction-methodology
├── thought://user-research-framework
├── execution://prd-writing-skills
├── knowledge://product-management-concepts
└── knowledge://industry-best-practices
```

**资源级依赖：**
```
contradiction-methodology依赖：
├── knowledge://marxist-philosophy
├── execution://contradiction-analysis-steps
└── knowledge://dialectical-thinking
```

**依赖解析机制：**

**自动依赖加载：**
```
1. 用户执行：promptx_action(product-manager)
2. PromptX解析product-manager.role.md
3. 发现引用：@thought://contradiction-methodology
4. 自动加载：contradiction-methodology.thought.md
5. 递归解析：该资源的所有依赖
6. 构建完整：角色的知识依赖图
7. 一次性加载：所有相关资源到AI上下文
```

**循环依赖检测：**
```
问题场景：
角色A引用资源X → 资源X引用资源Y → 资源Y引用资源X

解决机制：
- 依赖图分析：构建有向图检测环路
- 错误提示：明确指出循环依赖的路径
- 加载策略：跳过重复引用，避免无限循环
```

**版本管理与更新：**
```json
{
  "resource_id": "contradiction-methodology",
  "version": "1.2.0",
  "dependencies": [
    {"resource": "marxist-philosophy", "version": ">=1.0.0"},

  "compatibility": ["promptx>=0.2.0"]

```

**资源共享与复用：**

**跨角色共享：**
```
共享资源示例：
- user-research-framework：产品经理、UX设计师、市场研究员共用
- agile-development-process：产品经理、开发者、测试工程师共用
- data-analysis-methods：产品经理、数据分析师、运营专员共用

好处：
- 减少重复定义
- 保持方法论一致性
- 集中维护和更新
- 提高资源质量
```

**资源组合与定制：**
```xml
<!-- 基础用户研究框架 -->
<reference protocol="thought" resource="user-research-base">
通用的用户研究方法论
</reference>

<!-- 电商领域特化 -->
```

#### 4.4 协议继承与组合

**核心设计理念：**

DPML的继承与组合机制解决了AI角色定义中的一个关键矛盾：**专业化需求 vs 重复定义问题**。

**矛盾分析：**
- **对立面A（专业化需求）**：每个角色都需要独特的专业能力，不能千篇一律
- **对立面B（重复定义问题）**：很多角色有共同的基础能力，重复定义造成维护困难
- **载体转化**：继承与组合机制，既保持专业化又避免重复

**1. 基础继承语法**

```xml
<!-- 基础角色定义 -->
<role id="base-developer" file="base-developer.role.md">
  <role>
    我是软件开发工程师，专注代码质量和用户价值
    工作原则：代码可读性优先、测试驱动开发、持续学习
  </role>

  <thought>
    问题分析框架：需求理解 → 技术选型 → 架构设计 → 实现验证
    代码质量思维：可读性、可维护性、可扩展性、性能
  </thought>

  <execution>
    基础开发技能：代码编写、调试、测试、版本控制
    协作技能：代码审查、技术文档、团队沟通
  </execution>

  <knowledge>
    编程基础：数据结构、算法、设计模式
    工程实践：代码规范、测试方法、部署流程
  </knowledge>
</role>

<!-- 前端开发者继承基础开发者 -->
<role id="frontend-developer" extends="base-developer">
  <knowledge>
```

### 第五章：资源协议体系

#### 5.1 统一资源协议概念

**核心设计理念：**

统一资源协议（Unified Resource Protocol）是PromptX解决AI知识管理复杂性的关键创新。它解决了一个根本矛盾：**AI需要访问多样化资源 vs 缺乏统一访问机制**。

**矛盾分析：**
- **对立面A（多样化资源需求）**：AI需要角色定义、思维框架、执行技能、专业知识、工具手册等不同类型的资源
- **对立面B（访问机制混乱）**：不同资源有不同的格式、位置、引用方式，难以统一管理
- **载体转化**：统一资源协议，用类似URL的方式统一访问所有资源

**协议设计哲学：**

**1. 借鉴Web架构的成功经验**

**Web URL的启发：**
```
https://example.com/path/to/resource
协议://域名/路径/资源名

类比到PromptX：
@protocol://resource-id
@协议类型://资源标识符
```

**为什么这种设计成功？**
- **统一性**：所有资源都用相同的格式访问
- **可扩展性**：可以轻松添加新的协议类型
- **直观性**：一看就知道这是什么类型的资源
- **标准化**：建立了行业标准，便于生态发展

**2. 奥卡姆剃刀原则的体现**

**简洁统一的语法：**
```
传统方式（复杂）：
- 角色文件：./roles/product-manager.role.md
- 思维框架：./thoughts/user-research.thought.md
- 工具手册：./manuals/calculator.manual.md
- 知识库：./knowledge/agile-concepts.knowledge.md

PromptX方式（简洁）：
- @role://product-manager
- @thought://user-research
- @manual://calculator
- @knowledge://agile-concepts
```

**认知负担的降低：**
```
学习成本：一套语法规则适用所有资源类型
记忆负担：@协议://资源名的固定模式
使用便利：IDE可以提供智能提示和自动补全
```

**六大核心协议详解：**

**1. @role:// - 角色协议**

**用途**：引用完整的AI角色定义
```xml
<reference protocol="role" resource="product-manager">
完整的产品经理角色定义，包含四层DPML结构
</reference>
```

**应用场景：**
- 角色继承：`<role extends="@role://base-developer">`
- 角色组合：多个角色能力的融合
- 角色学习：AI学习其他角色的能力

**2. @thought:// - 思维协议**

**用途**：引用思维模式和分析框架
```xml
<thought>
<reference protocol="thought" resource="contradiction-methodology">
基于马克思主义矛盾论的分析框架
</reference>

<reference protocol="thought" resource="design-thinking">
以用户为中心的设计思维流程
</reference>
</thought>
```

**典型思维框架：**
- **contradiction-methodology**：矛盾分析方法论
- **data-driven-thinking**：数据驱动决策框架
- **user-research-methodology**：用户研究方法论
- **agile-mindset**：敏捷开发思维
- **design-thinking**：设计思维流程

**3. @execution:// - 执行协议**

**用途**：引用具体的执行技能和操作流程
```xml
<execution>
<reference protocol="execution" resource="user-interview-skills">
用户访谈的具体技能和操作步骤
</reference>

<reference protocol="execution" resource="code-review-process">

</reference>
</execution>
```

**技能分类：**
- **硬技能**：技术操作、工具使用、分析方法
- **软技能**：沟通协作、团队管理、项目推进
- **输出技能**：文档撰写、演示汇报、决策制定

**4. @knowledge:// - 知识协议**

**用途**：引用专业知识和概念体系
```xml
<knowledge>
```

**知识层次：**
- **基础概念**：领域内的核心术语和定义
- **方法论**：经过验证的最佳实践
- **技术栈**：具体的技术工具和框架
- **行业标准**：业界认可的规范和标准

**5. @manual:// - 手册协议**

**用途**：引用工具使用手册和操作指南
```xml

</reference>
```

**项目资源类型：**
- **团队信息**：成员角色、技能分布、协作方式
- **技术架构**：技术选型、架构设计、开发规范
- **业务背景**：项目目标、用户群体、商业模式
- **工作流程**：开发流程、发布流程、质量标准

**协议解析机制：**

**1. 资源定位流程**

## 📚 通俗易懂的统一资源协议理解

### 用生活中的例子来理解

#### 1. 图书馆管理系统的类比

**传统方式的问题：**
```
想象一个混乱的图书馆：
- 小说放在A区，但没有统一编号
- 技术书放在B区，用不同的分类方法
- 杂志放在C区，又是另一套规则
- 工具书放在D区，标签格式完全不同

结果：找一本书要跑遍整个图书馆，还不一定找得到
```

**PromptX的解决方案：**
```
统一的图书编号系统：
- @小说://三体          → 直接定位到科幻小说《三体》
- @技术书://React入门   → 直接定位到前端技术书
- @杂志://时尚周刊      → 直接定位到时尚类杂志
- @工具书://英汉词典    → 直接定位到语言工具书

优势：不管什么类型的书，都用相同的格式就能找到
```

#### 2. 手机通讯录的类比

**为什么手机通讯录好用？**
```
传统方式：记住每个人的电话号码（13812345678）
智能方式：给每个人起个名字（张三、李四、王五）

PromptX协议就像给AI资源起名字：
- @role://产品经理     → 就像通讯录里的"张三"
- @manual://计算器     → 就像通讯录里的"李四"
- @knowledge://前端技术 → 就像通讯录里的"王五"
```

#### 5.3 资源发现与学习机制

**核心设计理念：**

资源发现与学习机制解决了一个关键矛盾：**AI需要大量专业资源 vs 用户不知道有什么资源可用**。

**矛盾分析：**
- **对立面A（资源需求）**：AI要变专业，需要学习大量的角色、思维、技能、知识等资源
- **对立面B（发现困难）**：用户不知道系统里有什么资源，不知道该学什么
- **载体转化**：智能发现与学习机制，让AI能够自主发现和按需学习资源
